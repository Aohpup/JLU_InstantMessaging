## 4 消息怎么分开：长度前缀与接收缓冲区

TCP 只提供字节流。两次发送可以一起到达，一条文字也可以分多次到达，所以第二批采用：

```text
4 字节大端长度 N | 后面正好 N 个字节的内容
```

长度只统计后面的内容，不包含长度本身。内容固定为七行元数据，再接原样正文：

```text
1
TEXT
本发送端的连接标识
消息编号
发送者QQ
接收者QQ
Unix毫秒时间
正文（允许有换行，不再按行拆分）
```

HELLO、TEXT、ACK 使用同一组字段。HELLO 的消息编号为 `-`，正文为空；ACK 的编号填写被确认的 TEXT 编号，正文为空。协议版本当前固定为 1。

正文最多 16 KiB，帧内容最多 64 KiB；长度按 UTF-8 字节计，汉字不是一个字节。元数据只允许有限的字母、数字及分隔符，不能嵌入换行；正文检查非空白、有效 UTF-8，不引入 JSON 库。

`ChatProtocolLJY::feed` 的步骤：

1. 把这次 recv 的字节追加到 buffer_。
2. 不足四字节就继续等待；够四字节后读出长度。
3. 帧内容没凑齐就保留所有剩余字节；凑齐才 decode。
4. 解出一帧后继续检查下一帧，最后仅保留未完成的尾部。

即使一个汉字被拆成两段，也只是暂存在缓冲区，完整帧到齐后才按 UTF-8 校验。正常 EOF 时仍有半帧会报“尚有消息未接收完整”，不会显示残缺文字。

## 5 身份和 ACK 怎样工作

### 5.1 本地资格与网络握手分两步

主线程先调用 `makeChatIdentityLJY(session, peerQQ)`：本人必须已登录且当前服务为 QQ；通过既有 `friendAccount` 检查目标是好友，并拒绝本人。返回 ChatIdentityLJY，只包含两个号码副本，没有 Platform 指针、密码或 GUI 对象。

工作线程建立 TCP 连接后发送 HELLO。收到的 senderQQ 必须是自己选定的好友，receiverQQ 必须是本人，协议版本必须为 1。每个对端只接受一次 HELLO，之后每帧还要匹配该对端的连接标识。账号不符会报错并结束连接。

这验证的是双方本地记录和本次网络字段是否一致；课堂直连的自报号码不是密码学身份认证。身份快照也不会自动跟随主线程注销、切服务或好友删除而失效，第三、第五批的界面联动必须在这些操作发生时停止旧连接。

### 5.2 消息编号与旧连接隔离

每次 startChat 生成新标识：Windows 时间值、当前进程号、进程内连接序号。TEXT 编号再追加发方 QQ 和从 1 开始的消息序号。例如：

```text
连接标识-10001-1
连接标识-10001-2
```

双方各有自己的连接标识。收到 TEXT 时按对方标识、对方 QQ 和递增序号检查；ACK 携带被确认的编号，但 ACK 帧本身仍使用 ACK 发送端的连接标识。

所有返回事件也带本地连接标识。重连先停止并回收旧线程，再清空内部队列、生成新标识。调用者若先前已经取走旧事件，仍应比较事件的 connection 与当前标识；演示入口已经这样处理。消息标识用于课堂进程内与重连区分，不是全局账号发号服务。

### 5.3 四种状态的实际含义

| 状态 | 何时出现 |
| --- | --- |
| 发送中 | 主线程成功将文字放入待发队列 |
| 对端已接收 | 收到本次连接内、编号能对应已完整发出消息的 ACK |
| 发送失败 | 停止或断线时，该消息还没有向 Socket 成功提交过任何字节 |
| 结果未知 | 已提交过部分或全部字节，但连接结束前没有收到有效 ACK |

对端凑齐并验证 TEXT、放入 Incoming 事件队列后发送 ACK，因此它只表示对端网络模块接受了完整文字，不代表界面已经展示、用户已读或 SQLite 已保存。无法匹配待确认消息的 ACK 不改变状态；不同连接标识的帧直接拒绝。

不自动重发未知消息。否则第一次其实收到、只是 ACK 丢失时，再发会产生重复内容。

## 6 为什么后台等待不会卡住窗口

本批仍没有修改 GUI，但已提供第三批可用的接口：

```text
主线程：会话检查 → startChat → sendMessage 放入命令队列
                                  ↓
后台线程：非阻塞 Socket → select → 分段发送 / 累积拆包 / HELLO与ACK
                                  ↓
主线程：takeEvents 取出事件 → 将来由 Qt 刷新气泡、状态和提示
```

用 mutex 保护命令队列、事件队列及 ready_；网络等待在锁外进行。stopRequested_ 是原子停止标志。网络工作线程内部拥有一个局部 TcpPeerLJY 传输对象，套接字由该线程自行创建、使用和释放；外部对象只持有线程与队列，不从另一个线程直接关闭其套接字。

`ioctlsocket(FIONBIO)` 将 Socket 设为非阻塞。暂时不能读写时，WSAEWOULDBLOCK 表示等下一次机会，不是通信失败。select 最多等待 50 毫秒，再回到循环检查停止标志；非阻塞连接需观察可写和异常集合，并读取 SO_ERROR 判断结果。依据：[Microsoft select](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-select)、[Microsoft connect](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-connect)。

每条待发帧保留 offset；一次 send 少于本轮长度时，下次从实际发出的偏移继续。每轮只处理有限字节，然后回到停止检查，不把长文字塞进不可取消的 sendAll 循环。

stopChat 设置停止标志并 join；worker 正常收尾，给待发消息分配最终状态并发出 Closed 事件。析构也会停止线程，不使用 detach。主线程取到事件后再操作 GUI 或数据库；第三批拟用约 50 毫秒 QTimer 调用 takeEvents。

实际时间约定：

| 操作 | 约定 |
| --- | --- |
| 等待别人连接 | 无固定截止时间，可取消 |
| 主动连接 | 最多 10 秒 |
| TCP 建连后的 HELLO | 最多 5 秒 |
| 文字提交至工作线程后的发送及 ACK 总等待 | 最多 10 秒；超时结束连接并分配终态 |
| 单次 select | 最多 50 毫秒；不等于整个 stopChat 的严格耗时保证 |

静默网络故障在没有消息发送时不保证即时发现，本批没有心跳或自动重连。操作系统线程调度也可能影响停止耗时，验收按一秒内完成检查。

## 7 推荐代码阅读顺序

1. **ChatMessageLJY.h → ChatIdentityLJY.cpp**：认识消息字段和四种状态；看已有 SessionManager 如何提供身份验证，避免在网络线程重复写业务规则。
2. **ChatProtocolLJY.h → encode → feed → decode**：先看发出去的字节长什么样，再看分段和连续帧如何还原。不要直接从工作线程大循环开始读。
3. **TcpPeerLJY.h 的四个后台接口和 ChatEventLJY**：明确主线程只负责启动、提交文字、取事件和停止。
4. **p5_chat_demo.cpp**：看调用者怎样构造身份、启动网络、响应 READY、提交三条文字并处理事件。这与将来的 GUI 调用路径一致，只是现在打印文字。
5. **TcpPeerChatLJY.cpp 的 startChat/sendMessage/takeEvents/stopChat**：先读队列交接，再读 runChat 的监听连接分支。
6. **runChat 的发送与接收循环**：按“取命令 → 检查超时 → select → 推进发送偏移 → recv/feed → HELLO/TEXT/ACK → 收尾”阅读。
7. **两个验收文件**：协议测试解释分段场景；Python 脚本展示两个真实进程怎样互相验证。原始 Python 对端只为控制异常情况，不是产品服务器。

CMake 中 jlu_network 新增 ChatMessage、ChatProtocol、TcpPeerChat 源文件，并链接 ws2_32 与 Threads::Threads；jlu_core 只新增 ChatIdentity 会话适配实现。原终端和 GUI 仍没有调用聊天接口，发布版仍为已交付的 P4 版本。
