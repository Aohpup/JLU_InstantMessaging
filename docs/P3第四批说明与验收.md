## 1 现在怎样使用

在项目根目录编译并运行：

```powershell
cmake --preset local-debug
cmake --build --preset local-debug
.\build\debug\bin\jlu_im.exe
```

无参数启动使用 `D:/C_code/Cpp_test/JLU_InstantMessaging/data/jlu_im.db`。程序会显示实际绝对路径，自动建立缺失的目录和表，用户无需安装 SQLite 服务或手工建库。

数据库文件不存在时，首次保存 A—F 六名演示用户、12 个账号和 18 个群，并展示演示号码。已有文件只读取，恢复后从未登录状态开始；即使已有库没有人员，也不会重新灌入演示数据。演示密码仍是 `DemoOnly123!`。

| 操作位置 | 选项 | 作用 |
| --- | --- | --- |
| 未登录主菜单 | 4 保存数据 | 把完整平台状态写入数据库 |
| 登录后菜单 | 10 保存数据 | 保存所有已提交的业务修改，保留当前登录状态 |
| 登录后菜单 | 0 统一注销 | 只清理登录状态，不删账号、不执行保存 |
| 未登录主菜单 | 0 退出 | 保存成功后退出 |

退出保存失败时显示原因和保存位置，可选 `1 重试保存并退出`、`0 返回菜单`、`2 放弃未保存修改并退出`。选择放弃只丢弃内存中尚未保存的修改，磁盘保留上一次成功保存的版本。主动保存失败后仍留在菜单，可以继续操作或再次保存。

输入结束（例如脚本 EOF 或 Ctrl+Z）也会尝试保存；若失败，由于已无法继续输入，程序明确提示“本次修改未保存，程序异常退出”，返回码为 1。强制结束进程、关闭终端窗口不属于正常退出保存流程。

## 2 正常模式和测试模式

| 启动方式 | 初始数据 | 是否读写数据库 |
| --- | --- | --- |
| `jlu_im.exe` | 新库初始化演示数据，已有库读取原数据 | 使用项目 data/jlu_im.db |
| `jlu_im.exe --database "路径"` | 新库初始化演示数据，已有库读取原数据 | 只使用指定文件 |
| `jlu_im.exe --demo` | 每次重新生成演示数据 | 不读写任何数据库，退出清空 |
| `jlu_im.exe --empty` | 空平台，首个 QQ 号码仍从 10001 分配 | 不读写任何数据库，退出清空 |
| `jlu_im.exe --help` | 显示用法和默认路径，不进入菜单 | 不打开数据库 |

例如在隔离库中练习保存与重启：

```powershell
.\build\debug\bin\jlu_im.exe --database ".\build\debug\practice\练习.db"
```

默认路径由 CMake 的 `JLU_DEFAULT_DATABASE_PATH` 固定为配置时项目目录下的 `data/jlu_im.db`，因此从 VS Code、项目根目录或可执行文件目录启动都使用同一位置。指定的相对路径按当前工作目录解析，并显示解析后的绝对路径。复制可执行文件到其他位置不会改变编译进去的默认位置；移动项目后重新配置构建，或用 `--database` 明确指定位置。

Windows 入口使用 `wmain` 读取宽字符参数，CMake 在 MinGW 下加上 `-municode` 链接选项，使 `--database` 后的中文和空格路径能正确传入。数据库接口收到的路径仍统一是 UTF-8。

VS Code 原来的 `Debug jlu_im (GDB)` 无参数配置现在进入持久化模式；新增 `Debug jlu_im (演示内存模式)` 配置，便于每次从相同演示数据开始。`data/` 已加入 `.gitignore`，构建和旧测试仍使用 `build/` 中的隔离文件。

## 3 函数调用怎样连接起来

入口见 [main.cpp](../src/main.cpp)，菜单声明见 [ConsoleAppLJY.h](../src/ui/ConsoleAppLJY.h)，实现见 [ConsoleAppLJY.cpp](../src/ui/ConsoleAppLJY.cpp)。

```text
程序启动
  → 判断参数和数据库文件是否已存在
  → 新库：loadDemoDataLJY → storage.save
  → 已有库：storage.load
  → 创建 SessionManagerLJY
  → 创建 ConsoleAppLJY → run

菜单保存 / 正常退出
  → ConsoleAppLJY::saveData
  → 调用主程序传入的保存动作
  → SqliteStorageLJY::save(platform)
  → 事务提交后显示保存成功
```

菜单构造函数新增一个可选的 `std::function<void()> saveAction` 和用于展示的数据库路径。它表示“可以稍后调用、没有参数和返回值的保存函数”。主程序用下面这段 lambda 提供具体动作：

```cpp
if (storage) saveAction = [&] { storage->save(platform); };
ConsoleAppLJY app(session, std::cin, std::cout, saveAction, databasePath);
```

赋值时没有立即保存；菜单执行 `saveAction_()` 时才调用存储层。`[&]` 让这段动作使用主程序中已有的 storage 和 platform，它们都比菜单活得更久。内存模式不传保存动作，菜单就不显示保存入口。这样不需要增加新业务类，也不把 SQL 或平台容器操作放入菜单。

账号、好友和群的业务调用保持原样：菜单 → 会话 → 管理类 → 内存数据。只有明确保存或退出时才整体写回数据库，注销与切换服务都不自动保存。

`finish()` 集中处理退出：保存成功返回 0；保存失败选择返回菜单则返回 -1；输入结束且无法保存返回 1。析构仍只关闭数据库资源，不承担重要保存。
