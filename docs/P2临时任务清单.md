## 三、逐步任务

### 顺序 1：好友数据模型与容器

- [x] 建立 FriendRelationLJY，明确好友双方使用服务账号内部编号，不把人员编号或显示号码当作同一概念。
- [x] 用一份双向关系保存好友对，避免 A 加 B 与 B 加 A 产生两份矛盾数据；双方备注分别保存。
- [x] 在 PlatformLJY 中维护关系容器及只读查询入口，明确所有权。
- [x] 约定同服务约束、关系唯一性和删除时的备注清理规则。
- [x] 新建类使用独立 .h/.cpp 和 LJY 后缀；源码显式加入 CMake。

完成标准：构造两名测试人员及其服务账号，关系可从双方查询到，双方备注互不覆盖。此步骤完成后再实现具体菜单业务。

### 顺序 2：好友增删改查及最小菜单

- [x] 建立 FriendManagerLJY，提供添加、删除、修改本人备注、查询好友及好友资料的接口。
- [x] 沿用方案的课堂简化规则：选择对象并确认后建立双向关系，暂不增加好友申请审批系统。
- [x] 添加时拒绝不存在的账号、自己、重复好友和不同服务账号；删除时同步解除双方关系。
- [x] “修改好友”指修改自己对好友的备注，不能修改对方姓名、生日或用户昵称。
- [x] SessionManagerLJY 从已登录会话提供当前账号，菜单不让用户指定执行者编号。
- [x] 接入好友子菜单，支持返回；成功或整项失败后按任意键继续。

完成标准：A 在 QQ 中添加 B 后，A、B 均可查看关系；A 的备注修改不影响 B 的备注；删除后双方关系均消失。验证注销后不能操作好友。

### 顺序 3：共同好友与跨服务推荐

- [x] 区分两类查询：同一服务内两账号的共同好友，以及本人不同服务好友列表之间可关联的共同人员。
- [x] 将跨服务账号映射集中到明确接口，避免菜单通过昵称、姓名猜测同一人。
- [x] QQ↔微博依据共享号码和账号归属映射；涉及微信时要求有效的微信↔QQ 绑定。微信↔微博通过绑定的 QQ 及共享号码关联。
- [x] 源服务必须属于本人且已开通、当前目标服务必须已登录；目标好友也必须已开通目标服务。
- [x] 推荐列表排除自己、已是好友、未开通目标服务或缺少必要映射的对象，并说明无法推荐的原因。
- [x] 用户确认后检查选中对象，与顺序 2 的普通添加共用 createRelation 写入关系，不重建推荐列表或另写一套修改代码。
- [x] 接入共同好友查询和推荐菜单。

完成标准：A 的 QQ 好友 B 已开通并绑定微信时，能被推荐到 A 的微信；B 未开微信、未绑定或已是目标好友时，不会被误添加。共同好友结果按可验证的人员身份去重。

### 顺序 4：群模型与管理策略接口

- [x] 建立 GroupLJY、GroupMemberLJY，保存稳定内部群编号、所属服务、可见群号、名称、群主、成员及管理员标记。
- [x] 预留父群编号与当前管理模式字段；群主必须是该群成员，成员必须开通群所属服务。
- [x] 建立抽象 GroupPolicyLJY 及 QQGroupPolicyLJY、WeChatGroupPolicyLJY，通过虚函数表达申请、邀请、踢人、管理员及子群权限。
- [x] 群成员等业务数据由群对象保存，策略对象只负责判断规则，不能各存一份成员名单。
- [x] 沿用方案约定：微博默认采用 QQ 风格；明确这属于本项目设计选择。
- [x] 确定 GroupManagerLJY 负责协调验证与修改，策略不直接修改平台容器。

完成标准：通过基类接口即可体现 QQ、微信的权限差异；替换策略对象不会触碰群成员数据。此步骤不提前实现顺序 9 的完整切换流程。

- [x] 增加独立演示初始化模块，通过账号、好友和群的业务接口构建虚构人员 A—F 及所需服务，不能直接绕过规则写私有容器。

### 顺序 6：QQ 群成员与管理员操作

- [x] 通过 GroupRequestLJY 保存入群申请、申请人、目标群及待处理状态，拒绝重复未处理申请和重复入群。
- [x] 群主或管理员审批申请；审批时重新检查申请人账号、群及成员关系，不能只在提交申请时校验。
- [x] 实现普通成员退群、群主转让后退群、群主或管理员踢人。
- [x] 群主可以设置或取消管理员；管理员不能踢群主、不能任免其他管理员。
- [x] 补充同级管理员边界：已采用“管理员不能踢其他管理员，群主也须先取消目标管理员身份再移除”，避免同级权限不明确。
- [x] 所有操作检查当前身份与群归属，拒绝非成员管理、未登录操作及跨服务成员加入。
- [x] 接入申请、审批、退群、踢人、转让和管理员菜单。

完成标准：用群主 A、管理员 B、普通成员 C 演示权限；同一操作由不同角色执行时结果正确。群主不能直接退出造成无主群。

### 顺序 7：微信群邀请与权限差异

- [x] 微信策略拒绝主动申请入群；由现有成员发出邀请，被邀请人确认后加入。
- [x] 复用请求模型区分“申请”和“邀请”，保存邀请人、被邀请人及目标群。
- [x] 发出和接受邀请时都检查邀请人仍为群成员；被邀请人必须开通该群所属服务且尚未入群。
- [x] 群主可踢人和转让群主；普通成员可以邀请、查看和退群，不能执行群主管理动作。
- [x] 微信策略不允许设置管理员或创建子群。
- [x] 接入邀请、接受、拒绝菜单；注销或取消输入不能提前改变成员名单。

完成标准：C 不能通过主动申请进入微信群，但可接受现有成员 B 的邀请；B 在邀请接受前退出后，该邀请不能再让 C 入群。

### 顺序 8：QQ 子群及父子群一致性

- [x] 仅 QQ 管理策略下的顶级群允许建立子群；由父群群主发起，不增加管理员创建子群权限。
- [x] 创建时指定有效子群群主，子群群主和其他成员必须都是父群成员。
- [x] 只允许一级子群，拒绝对子群再建子群。
- [x] 父群成员退出或被踢时，同步移除其子群成员资格。
- [x] 若离开的人员担任子群群主，先完成转让，否则拒绝整项退出或踢人操作。
- [x] 先检查所有受影响子群，再统一修改；任一约束不满足时，父群与各子群均保留原状态。
- [x] 接入子群创建与查询菜单。

完成标准：普通成员离开父群后，其子群成员资格同步移除；涉及子群群主时整项操作被拒绝，不发生部分群已删除、部分群未处理的情况。

### 顺序 9：动态切换群管理模式

- [x] 当前群已有申请保留，但当前策略不允许的审批暂停；当前群邀请在接受时仍检查模式与人员资格。

- [x] 微信→QQ 后恢复当前群管理员权限，已有子群及其请求仍保留，可继续操作并创建新子群。
- [x] 菜单明确显示“所属服务”和“当前群管理模式”，切换不把 QQ 账号变成微信账号，也不迁移到微信的同号群。

## 四、开发批次：哪些步骤放在一起做

实际推进以本节的六个批次为单位；第三节的十个顺序保留，用于追踪批次内部的工作。适合合并的是 **1＋2、4＋5、6＋7、8＋9**；顺序 **3、10** 单独执行。

同一批内的步骤一起安排开发与交付，但仍按依赖顺序实现。先完成前一步的关键规则验证，再做后一步，最后统一验收本批。每批验收通过后再进入下一批；批次完成必须包含必要的菜单接入、针对性测试和文档更新。

| 批次 | 放在一起的顺序 | 合并或单独安排的理由 | 本批交付与验收重点 |
| --- | --- | --- | --- |
| 第一批：好友基础功能 | 1 → 2 | 好友数据结构直接服务于增删改查，配合实现可以及时验证容器设计，交付可操作的功能 | 数据模型、关系容器、业务接口与好友菜单；验证双向添加/删除、双方备注独立及身份限制 |
| 第二批：共同好友与推荐 | 3，单独做 | 依赖第一批稳定的关系数据，额外涉及跨服务账号映射和绑定条件，单独验收便于定位错误 | 同服务共同好友、跨服务共同人员与推荐菜单；验证去重、绑定映射和无效对象过滤 |
| 第三批：群基础与演示数据 | 4 → 5 | 群模型、策略接口和群容器需要配合查询及样例数据验证，单独交付空接口不便检查设计 | 群模型、策略接口、18 个演示群和查询菜单；验证群号按服务区分、有效群主及初始化约束 |

## 五、阶段演示主线

1. A 在 QQ 中添加 B、C，修改对 B 的备注，切换 B 检查双方关系与备注互不干扰。
2. 为相关人员准备服务及有效绑定，查询共同好友，将符合条件的 QQ 好友推荐到微信，再验证重复推荐被排除。
3. 查看 QQ 和微信各自的 1001 群，展示同号群彼此独立。
4. 展示 QQ 的申请与审批，再展示微信的邀请与接受；分别尝试不允许的入口。
5. 对照群主、管理员、普通成员执行踢人、管理员设置及退出，检查权限拒绝结果。
6. 建立子群，验证父群成员退出时的联动，以及子群群主尚未转让时的整项拒绝。
7. 对同一个群执行 QQ→微信→QQ，比较主群成员与管理员标记，验证权限暂停及恢复、子群及其请求继续保留。
8. 统一注销，确认受保护操作不可继续；正常退出。此阶段不演示重启恢复。

## 六、开发约定

- 类名统一 LJY 后缀，每个自定义类独立文件；常规编号优先使用 int，确需更大范围时使用 unsigned long long，不引入 cstdint。
- 函数、类和关键定义的注释使用简洁的简体中文，优先写在头文件，保留普通 //，不使用 @brief 等标签。
- 控制台负责输入与展示，会话确定执行者，业务类检查规则，平台或实体拥有数据；不让菜单直接修改私有容器。
- 复用已有账号、日期和身份验证接口；身份关联依据有效账号映射，不能通过姓名、昵称或用户手填执行者编号绕过归属限制。
- 每步只增加当前需要的接口与文件，不为尚未开始的功能提前堆积空类。表中的类名与拆分可在实施前按实际复杂度微调，并同步本清单。
