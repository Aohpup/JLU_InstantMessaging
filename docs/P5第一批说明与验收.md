## 3 Socket、IP、端口分别是什么

**Socket 是程序使用网络的一种接口。** 程序通过 `socket()` 向 Windows 申请一个套接字，然后用它连接和传送字节。`SOCKET` 是 Windows 规定的句柄类型，可理解为操作系统发给程序的资源标识，不是 QQ 号码，也不需要自己换成 int。

**IP 标识网络地址，端口区分该地址上的网络服务。** `127.0.0.1` 是本机回环地址，两端必须运行在同一台电脑才能按上述命令相连。`27015` 是本次监听入口，与账号 10001、10002 无关。连接端通常由系统自动分配自己的本地端口，不必也绑定 27015。

**TCP 负责可靠、有序地传送字节流。** 它不会自动附带“这条消息由哪个 QQ 发来”或“这里是下一条消息”的业务含义。账号、消息边界和接收确认要由第二批应用协议定义。SQLite 的用途则是保存数据；它不会替两端建立连接，本批完全不需要数据库。

同一套程序提供两个角色：A 先等待，B 主动连接。这个区别只体现在建连过程；连好后双方都能发送与接收，不是 A 只能收、B 只能发。

## 4 一次运行的调用过程

```text
终端 A                                       终端 B
wmain → runDemo                              wmain → runDemo
  TcpPeerLJY：WSAStartup                       TcpPeerLJY：WSAStartup
  startListening                              connectTo
    socket → bind → listen                      socket → connect
  acceptConnection ←────── TCP 建连 ───────────────┘
    accept 返回一个新的连接套接字
    关闭监听套接字

  sendAll ────────────── 文字 A ───────────────→ 接收缓冲区
  接收缓冲区 ←────────── 文字 B ──────────────── sendAll
  finishSending                               finishSending
  循环 receiveSome                            循环 receiveSome
  累积到对端结束发送，显示文字                  累积到对端结束发送，显示文字
  close → 析构 → WSACleanup                    close → 析构 → WSACleanup
```

图中收发可能交错发生，两端互不共享内存；实际打印的先后顺序也不要求一致。

### 4.1 初始化和创建套接字

构造 `TcpPeerLJY peer;` 时调用 `WSAStartup(MAKEWORD(2, 2), &data)`，请求使用 Winsock 2.2。它只是初始化网络环境，并没有开始监听。其错误码直接来自返回值；其他 Socket API 的失败通常通过 `WSAGetLastError()` 获取错误码。

`socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)` 分别表示 IPv4、流式套接字、TCP。成功后返回可用句柄，失败返回 `INVALID_SOCKET`。

`makeAddress` 将文本 IP 和整数端口装进 `sockaddr_in`：`inet_pton` 转换 IPv4 文本；`htons` 将端口转成网络字节序。读取实际端口时用 `ntohs` 反向转换。名称中的 `h` 是主机、`n` 是网络，`s` 对应短整数；不是字符串处理。

### 4.2 为什么有两个 SOCKET 成员

| 成员 | 作用 | 何时关闭 |
| --- | --- | --- |
| listener_ | 在指定 IP 和端口等待有人连接 | 接受一个对端后立即关闭，或失败、对象释放时关闭 |
| connection_ | 已建立的 TCP 连接，用来 send/recv | 本次交换结束、主动 close 或对象释放时关闭 |

监听侧执行 `bind → listen → accept`。`bind` 确定本地地址，`listen` 开始接受连接请求，`accept` 等待并返回一个新的连接套接字；原监听套接字不会自动变成连接套接字。本批一次只服务一个对端，所以接受成功后关闭 listener_，已建立的 connection_ 仍可正常收发。

主动连接侧执行 `socket → connect`，直接使用 connection_，不需要创建自己的监听口。`startListening` 返回实际端口；自动验收传 0 让系统选空闲端口，再把返回的端口交给另一个进程，避免测试写死端口冲突。

`SO_EXCLUSIVEADDRUSE` 使监听地址由当前套接字独占，重复启动相同监听能明确报错。这里仅是一个套接字选项，没有额外设计端口管理系统。

### 4.3 为什么发送要用 while

`send` 返回本次实际交给网络栈的字节数，可能少于要求发送的数量。因此 sendAll 维护 `offset`：

```cpp
while (offset < text.size())
{
    // 每轮最多提交 4096 字节，实际 count 以 send 返回值为准。
    const int count = send(connection_, text.data() + offset, length, 0);
    // 实际代码在这里处理错误和零进展。
    offset += count;
}
```

上面是结构摘录，`length` 的计算及错误处理请看原文件。例如需要发送 100 字节，本轮只完成 60，下一轮从第 60 字节继续传余下的 40，而不是从头重发。

sendAll 成功只说明本端完成了这次发送操作，不能据此显示“对方已读”或“对端应用已确认”。第二批会增加 ACK。依据：[Microsoft send 文档](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-send)。

### 4.4 为什么接收也要用 while

`receiveSome` 中 `recv` 的返回值有三种含义：

| 返回值 | 本批处理 |
| --- | --- |
| 大于 0 | 按实际字节数构造 string，交给调用者累积 |
| 等于 0 | 对端正常结束发送，返回空串，演示接收循环结束 |
| SOCKET_ERROR | 抛出包含中文原因和 Winsock 编号的异常 |

`std::string(buffer, count)` 按实际数量复制字节，不要求 buffer 末尾有 `\0`。用 `std::string(buffer)` 会错误地假定网络数据已带字符串结束符。

网络可能将一个汉字的 UTF-8 字节拆到两次接收里。这里先把所有字节追加到 received，完成后统一显示，不在中间对半个汉字进行解码。依据：[Microsoft recv 文档](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-recv)。

### 4.5 第一批如何知道文字发送完了

每端 sendAll 后调用 `finishSending()`，内部执行 `shutdown(connection_, SD_SEND)`：本端不再发送，但仍能接收。当对方读完已发送字节后，对方的 recv 会返回 0。两端都如此操作，便能各发一段、各收一段，再关闭连接。

这是 TCP 的“半关闭”。它不会直接释放套接字，最终还需要 closesocket。依据：[Microsoft shutdown 文档](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-shutdown)。

**本批以结束发送作为单次文字结束的标志，不能据此连续发送第二条。** 如果两边只调用 recv 却都不结束发送，就可能一直等待。第二批将改用长度前缀划分多条消息，让连接保持打开；不要把 finishSending 插入未来每次点击发送按钮的逻辑。

演示限制为短文字并采用“先发后收”。这便于观察最小流程，不是未来连续聊天的收发调度方式；第二批再用后台非阻塞收发处理等待和多条消息。

### 4.6 失败后为什么能释放资源

网络类的析构函数先 close，再 WSACleanup。peer 是 runDemo 内的局部对象：正常返回会析构；收发抛异常、离开作用域时也会析构，随后 wmain 捕获异常并输出“操作失败”。这就是用对象生命周期管理资源。

close 检查句柄是否有效，关闭后将其设回 INVALID_SOCKET，所以显式 close 后再执行析构不会重复关闭同一个句柄。监听或连接过程失败时还会立即 close，让已经创建的套接字尽快释放。禁止复制对象，是为了防止两个对象误以为自己拥有同一组句柄而重复释放，并非所有普通业务类都要禁止复制。

当前 accept、connect、recv 是阻塞调用，没有自定义的短超时或跨线程取消机制。析构负责操作已经返回或抛错后的清理，不承诺能中断一个仍在等待的调用。第二批会解决后台线程、有限等待和停止；GUI 接入前必须完成这一点。

## 5 CMake 怎样生成这个程序

```cmake
add_library(jlu_network STATIC src/network/TcpPeerLJY.cpp)
target_include_directories(jlu_network PUBLIC "${CMAKE_CURRENT_SOURCE_DIR}/src")
target_link_libraries(jlu_network PUBLIC ws2_32)

add_executable(p5_socket_demo tests/p5_socket_demo.cpp)
target_link_libraries(p5_socket_demo PRIVATE jlu_network)
```

第一句将网络实现编译成静态库。第二句让程序能写 `#include "network/TcpPeerLJY.h"`。第三句指定 Windows Socket 链接依赖；只有头文件声明还不够，链接器也要知道网络函数由哪一个系统库提供。PUBLIC 会让使用 jlu_network 的目标一并取得必要的包含目录和链接依赖。

演示入口单独编译，再链接 jlu_network 和 ws2_32。构建关系是：

```text
TcpPeerLJY.cpp → jlu_network 静态库 ──┐
Windows ws2_32 ──────────────────────┼→ p5_socket_demo.exe
p5_socket_demo.cpp → 入口目标文件 ───┘
```

MinGW 额外的 `-municode` 用来选择宽字符 wmain 入口，命令行中文再通过 WideCharToMultiByte 转为 UTF-8。它不是网络协议选项。

原 jlu_im 仍链接 jlu_console / jlu_core，原图形程序的链接关系也没改。本批没有把网络库硬接进业务核心。演示目标放在 BUILD_TESTING 条件下，local-debug 和 gui-debug 均已开启；现有 gui-release 关闭了测试目标，因此本批没有更新 P4 发布包。

Python 仅用于自动启动和检查两端，不参与 C++ 收发。CMake 找到 Python 时注册 p5_socket 这个 CTest；找不到仍可编译并按前文手动演示。本机已找到解释器，不需要用户另装。

## 6 推荐代码阅读顺序

按以下顺序读即可，不用先翻旧业务代码：

1. **TcpPeerLJY.h**：先看类注释、公开操作及两个 SOCKET 成员。理解哪些操作负责建连、哪些负责收发；复制删除声明不是业务操作。
2. **p5_socket_demo.cpp 的 runDemo**：先跳过 utf8 小函数，从 `TcpPeerLJY peer` 往下看。确认角色分支之后，两端共用 sendAll → finishSending → receiveSome 循环 → close。
3. **TcpPeerLJY.cpp 的构造、close、析构**：看资源从哪里来、在哪里释放。再看 `throwSocketError` 如何将常见错误码转成中文。
4. **startListening、acceptConnection、connectTo**：对照第 4 节的双端流程图，区分 listener_ 与 connection_。最后再补读 makeAddress 中的 IP 与端口转换。
5. **sendAll、receiveSome、finishSending**：理解偏移量、实际字节数、TCP 字节流和半关闭；这是下一批消息协议的基础。
6. **CMakeLists.txt 的 jlu_network 和 p5_socket_demo 部分**：对应编译、包含目录、系统库和可执行入口，不必重读全部旧目标。
7. **p5_socket_acceptance.py**：最后了解自动验收。start 启动独立程序，ready 等待监听就绪，finish 收集退出码和输出。Python 日志读取线程只为验收服务，不是产品的网络工作线程。

可以先用笔回答三个问题：A 为什么拥有两个套接字？一次 recv 为什么不一定是一条消息？shutdown(SD_SEND) 与 closesocket 有何区别？能讲清这三点，就掌握了第一批的核心。
