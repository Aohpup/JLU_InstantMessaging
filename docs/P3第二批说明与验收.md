## 2 加入数据库后，原函数调用有什么变化

### 2.1 加好友等业务调用仍然保持原样

以实际已有的添加好友为例：

```text
ConsoleAppLJY::addFriend()
  → SessionManagerLJY::addFriend(对外号码)
  → FriendManagerLJY::addFriend(本人编号, 本人账号编号, 对方账号编号)
  → FriendManagerLJY::createRelation(...)
  → PlatformLJY::friendRelations_.emplace(...)
```

这条链仍只负责输入、确定操作者、检查规则和修改内存。注册、修改资料、设置管理员、释放子群也沿用原链路。本批没有把 SQL 塞进这些函数，没有让 addFriend 每调用一次就单独 INSERT。

所以“好友添加成功”目前只表示内存修改成功；它与“数据库保存成功”是两个不同结果，不能合并理解。

### 2.2 新增一条明确的保存调用链

```text
本批验收程序
  → SqliteStorageLJY storage(数据库路径)
      → sqlite3_open() 打开/创建文件
      → PRAGMA foreign_keys=ON 开启外键
      → 事务内执行建表 SQL，已有表和记录保留
  → storage.save(platform)
      → BEGIN IMMEDIATE 开始保存事务
      → 清理本项目旧数据
      → 逐表读取 platform，绑定参数并写入
      → COMMIT 成功提交；出错则 ROLLBACK
  → storage 析构
      → 释放语句、关闭连接
```

当前正式 main 和 ConsoleApp 还没有创建 storage，也没有调用 save；实际调用者是本批测试程序。不能因为类已编译进项目，就认为菜单操作已经自动落盘。

以下片段展示当前可用的接口，需放在能链接 jlu_core 的 C++ 目标中；它不是已修改的主程序：

```cpp
#include "services/DemoDataLJY.h"
#include "storage/SqliteStorageLJY.h"

PlatformLJY platform;
loadDemoDataLJY(platform);
SqliteStorageLJY storage("build/debug/lesson.db");
storage.save(platform);
```

`save(const PlatformLJY&)` 接收完整平台的只读引用：它读容器并写数据库，不修改平台、会话或用户当前操作。若已有数据库，必须传入真正准备保存的完整平台；未来启动加载完成前不能拿空平台直接覆盖它。

### 2.3 构造和析构并不等于保存

| 调用 | 做什么 | 是否把平台内容写入数据库 |
| --- | --- | --- |
| SqliteStorageLJY(path) | 建立连接、开启外键、补建缺失表和初始编号行 | 否；已有记录保留 |
| 原会话/业务方法 | 校验业务并修改 PlatformLJY | 否 |
| storage.save(platform) | 一次保存平台的完整持久数据 | 是，成功提交后生效 |
| ~SqliteStorageLJY() | 释放当前语句和连接 | 否 |

构造失败会关闭已经打开的连接并抛出错误；错误文件不会被当成空库重新覆盖。已有库的架构升级仍不在本批范围内。

## 3 save 内部具体怎样调用 SQLite

一张表准备一次 INSERT，每一行依次执行：

```text
prepare(SQL) → sqlite3_prepare_v2
bind(1, 编号)、bind(2, 文本)... → sqlite3_bind_int / sqlite3_bind_text
writeRow() → sqlite3_step → sqlite3_reset → sqlite3_clear_bindings
换下一张表 → 释放旧语句，再 prepare
```

以人员表为例，INSERT 的四个问号分别绑定 personId、name、birthDate、location。数据库使用实际字符串值，不把“中文 O'Brien”之类输入当 SQL 代码。顶级群没有父群时调用 sqlite3_bind_null；其余群写真实父群内部编号。

资源使用完调用 sqlite3_finalize，最终由析构调用 sqlite3_close。连接禁止复制，避免两个对象重复关闭同一个句柄。只由存储类访问平台私有容器和凭据，其他实体继续使用已有 getter，不给全部实体增加公开 setter。

## 4 保存顺序与失败处理

本项目数据量小，采用整批替换九张表内容。删除和插入都在同一个事务中，只处理本项目定义的表，其他表不受影响。

清理顺序：请求 → 群成员 → 子群 → 顶级群 → 好友 → 绑定 → 凭据 → 账号 → 人员 → 编号状态。

写入顺序：人员 → 账号 → 凭据 → 绑定 → 好友 → 顶级群/子群 → 群成员 → 请求 → 编号状态。

这样外键始终可以开启。父群先于子群保存；成员额外保存原 vector 顺序；凭据、双方备注、已暂停的管理员标记、请求状态和六个发号计数器都包含在内。登录状态、密码登录历史和策略对象不保存。

主群转微信后，内存已经释放子群和其请求；下一次 save 按当前状态重写，旧子群的成员与请求也从数据库中清除，但 last_group_id 不倒退。

如果保存后半段失败，catch 中先释放语句，再执行 ROLLBACK，然后重新抛出原错误。磁盘回到上次成功保存的状态；内存中的新修改仍在，调用者可以重试。该保证针对一次保存事务，不表示内存修改已自动保存，也不保证未保存数据在强制结束后仍存在。

## 5 与后续调用流程的关系

第三批会实现“从数据库还原到 PlatformLJY”，届时才能组成完整的保存—读取往返。第四批再安排：启动加载 → 创建会话与菜单 → 业务修改内存 → 用户保存或正常退出时调用 save。

这两个环节目前尚未实现，不存在可用的 load 方法或正式保存菜单。P4 图形界面后续复用同一个会话、业务和存储接口，无需重新写 SQL。

## 6 本批验收结果

构建成功，日志无告警；CTest 11 个测试程序全部通过：原有 72 组业务场景、第一批 SQLite 接入验证，以及本批新增 3 组集成场景。

| 场景 | 实际验证 | 结果 |
| --- | --- | --- |
| 完整保存与再次打开 | 六人、十二账号、密码、绑定、独立备注和引号文本、群成员顺序、申请/邀请；重新构造存储对象不清空原库 | 通过 |
| 子群释放后的保存 | 子群、成员和请求删除；发号状态不回退，主群管理员标记保留，平台内存不被保存操作改动 | 包含在第一组，通过 |
| 保存中途失败和重试 | 测试专用触发器在写入请求时制造失败，九表快照与旧状态一致；内存昵称修改仍在，移除触发器后重试成功；显式保存空平台也正常 | 第二组通过 |
| 非数据库文件 | 打开失败并抛出错误，原文件字节保持不变；空路径拒绝 | 第三组通过 |

故障触发器只存在于测试，不进入生产存储实现。验收使用独立 SQL 连接读取磁盘结果，不把 SQL 检查说成已经实现平台加载。没有改动按键处理，因此不重复原生控制台专项测试。
