## 1 十张表与现有对象

| 表 | 字段 | 对应数据与约束 |
| --- | --- | --- |
| persons | person_id、name、birth_date、location、avatar_color | PersonLJY；person_id 主键 |
| service_accounts | account_id、person_id、service、external_id、nickname、applied_on | ServiceAccountLJY；person_id 引用人员；同人同服务唯一，服务＋对外号码唯一 |
| credentials | person_id、password | PlatformLJY.credentials_ 与 PasswordCredentialLJY；每人一份凭据，person_id 同时为主键和外键 |
| account_bindings | wechat_account_id、qq_account_id | PlatformLJY.weChatToQQ_；微信为主键，QQ 唯一，两者都引用内部账号编号 |
| friendships | first_account_id、second_account_id、first_remark、second_remark | FriendRelationLJY；前小后大的编号对作为主键，分别保存双方备注 |
| friend_requests | first_account_id、second_account_id、sender_account_id、recipient_account_id、state | FriendRequestLJY；有序账号对为主键，每对保存最近一次申请；双方引用账号，发送与接收方向单独保存 |
| chat_groups | group_id、service、number、name、owner_account_id、style、parent_group_id | GroupLJY；内部编号主键，服务＋可见群号唯一；群主引用账号，父群引用群 |
| group_members | group_id、account_id、is_administrator、member_order | GroupLJY.members_ 中的 GroupMemberLJY；群＋账号主键，保留 vector 顺序 |
| group_requests | request_id、service、group_number、type、sender_number、target_number、state | GroupRequestLJY；请求编号主键；服务＋群号/号码组合外键与当前类保持一致 |
| id_state | singleton、last_person_id、last_account_id、last_shared_number、last_wechat_number、last_group_id、last_group_request_id | 平台六个最后已分配编号；singleton 固定 1，只有一行 |

十张表都直接对应现有数据，不增加聊天表、服务目录表或权限表。群成员单独成表是因为一个群有多名成员，不把成员列表拼成一串文本。

## 2 数据表示

- avatar_color 为 0—5 的预设色索引；默认 -1 沿用人员编号循环色。旧库自动补此字段，保存写入实际色号，表总数仍为十张。
- 编号使用 INTEGER，对外账号号码使用 TEXT，以兼容 wx_20001。群的可见号码仍为整数。
- QQ、微信、微博分别保存为 service 0、1、2，与现有 ServiceTypeLJY 一致。
- 群模式 QQ、微信分别为 style 0、1；申请/邀请分别为 type 0、1；待处理/同意/拒绝/失效分别为 state 0、1、2、3。
- 好友申请 state 为 0 待处理、1 已同意、2 已拒绝；拒绝后重新申请覆盖此账号对的旧记录，同意后才写入 friendships。
- 布尔管理员标记为 0/1；成员展示顺序 member_order 从 0 起，读取按它排序。
- 日期使用 YYYY-MM-DD 文本；注册年龄仍根据申请日期计算，不重复保存计算结果。
- C++ 顶级群的 parentGroupId 为 0，数据库使用 NULL 表示没有父群。读写时转换，避免虚构一条编号为 0 的父群记录。
- QQ/微博共享号码保存在各自账号的 external_id，业务确保同一人两个服务的号码一致；persons 不额外保存重复的共享号码。
- 凭据表按已批准的课堂方案保存密码字符串；第二批通过存储类友元权限保存课堂凭据，不增加公共密码 getter。

## 3 数据库约束与业务规则

主键负责唯一定位一行；UNIQUE 防止重复开通服务、重复号码、重复绑定和重复成员顺序；外键保证引用的人员、账号或群确实存在。每次连接显式执行 PRAGMA foreign_keys=ON，不能只在首次建库时设置。

下列规则继续由业务及加载检查负责，不为课设增加触发器体系：好友同服务；绑定必须是同一人的微信和 QQ；QQ/微博共享号码；群主属于群且与群同服务；子群与父群同服务、只允许一级、子群成员属于父群；日期有效及枚举间的操作权限。

请求记录引用账号和群，而不引用群成员：邀请对象在接受前本来就不是群成员；历史已处理请求也可能对应已离群账号。因此不能把“请求目标必须已经是成员”写成约束。

## 4 写入、读取与清理顺序

建表顺序已体现在 SQL 文件：人员 → 服务账号 → 凭据 → 绑定 → 好友 → 群 → 群成员 → 群请求 → 编号状态 → 好友申请。表创建使用 IF NOT EXISTS，初始编号行使用 INSERT OR IGNORE，不在建表脚本中清空已有数据。

一次完整保存放在一个事务中。清理旧记录按：好友申请 → 群请求 → 群成员 → 子群 → 顶级群 → 好友 → 绑定 → 凭据 → 账号 → 人员 → 编号状态。再按依赖顺序写入，群先父后子，最后保存实际计数器并提交。无需关闭外键来规避顺序问题。

读取先检查外键，再读人员、账号、关系和群；群按内部编号还原，全部群读完再检查父子关联，成员按 member_order 恢复，最后恢复发号状态。群主在实体构造时会自动入群，因此先清空默认成员，再还原成员表，避免重复。数据先进入临时平台，必要归属和计数器检查通过后才替换正式平台；调用方须在创建会话前加载。

id_state 的初始六值为 0、0、10000、20000、0、0。以后保存平台实际值，不能用这些初值重置已有库，也不能只计算 MAX(id)：例如删除内部编号 19 的子群后，last_group_id 仍应为 19，下次从 20 分配。

2026-10-12 起，主群转微信保留既有子群、成员和请求，保存和读取须保留其父子关系；加载不再要求已有子群的父群必须处于 QQ 模式。新建子群仍由业务层要求 QQ 模式。当前 SQL 没有隐式级联删除，由存储代码按上述顺序明确完成。

旧库打开时自动执行 CREATE TABLE IF NOT EXISTS 补充 friend_requests，并检查 persons 字段，缺少 avatar_color 时 ALTER TABLE 补建；不删除已有表或关系，也不重置发号状态。好友申请和其他数据一起保存、回滚、读取，账号对作为主键，因此 id_state 不增加计数器。
