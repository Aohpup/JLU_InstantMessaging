# P1 第 3 和第 4 步说明

日期：2026 年 9 月 9 日。本文说明第 3、4 步的底层账号与容器接口；第 5、6 步已接入登录会话和菜单，见 [后续说明](P1第5和6步说明.md)。当前仍不连接 MySQL、不读写业务文件。

## 调用关系

正式程序调用关系：ConsoleApp → SessionManager 从已验证会话取得身份 → AccountService 校验和修改 → Platform 保存数据。下列底层示例用于学习和测试，不作为菜单的权限入口。

PlatformLJY 使用 map 保存人员和账号，拥有三个服务对象以及微信到 QQ 的绑定关系。它只公开 const 查询指针；AccountServiceLJY 作为友元统一执行修改，没有对外暴露容器写入口。map 插入不会使已有元素地址失效，当前不提供删除接口；查询指针不拥有数据，必须在平台仍存在且未移动时使用。

AccountServiceLJY 持有平台的引用。多个 AccountServiceLJY 使用同一个平台时，也使用同一组计数器。PersonLJY 和 ServiceAccountLJY 的构造函数仍可单独用于学习，但直接构造对象不会自动存入平台；正式数据通过 AccountServiceLJY 创建。

## 接口与使用顺序

```cpp
PlatformLJY platform;
AccountServiceLJY manager(platform);
int personId = manager.createPerson("Demo A", "2005-03-12", "Changchun");
int weiboId = manager.openService(personId, ServiceTypeLJY::Weibo, "Weibo A");
int qqId = manager.openService(personId, ServiceTypeLJY::QQ, "QQ A");
int weChatId = manager.openService(personId, ServiceTypeLJY::WeChat, "WeChat A");
manager.bindWeChatToQQ(personId, weChatId, qqId);
```

返回的编号是内部账号编号，和对外 QQ／微信号码不同。用 platform.findAccount(qqId) 查询账号，再通过 externalId() 取得对外号码。findAccount(serviceType, externalId) 同时使用服务与号码定位，避免 QQ 和微博同号时产生歧义。

其他接口：updateProfile 修改姓名、生日和所在地；updateNickname 只修改本人账号昵称；accountsForPerson 列出一个人的账号；findAccountForPerson 查询是否已开某项服务；boundQQForWeChat 查询已绑定的 QQ；registrationAge 按该服务申请日期计算 注册年龄。单项查询找不到时返回 nullptr，账号列表找不到时为空；调用前要检查结果。

## 号码及资料规则

- 人员编号和内部账号编号从 1 自动增长；QQ／微博共享号码从 10001 开始，微信为 wx_20001 等独立号码。
- 谁先开通 QQ 或微博，谁触发共享号码的首次分配；另一服务复用此号码。不同人的共享号码不同。
- 每人每服务只能开通一次；绑定不新建或合并账号，不修改已有号码。
- 日期必须是合法 YYYY-MM-DD，正确处理闰年；生日和申请日期不得晚于业务参考日期，申请日期不得早于生日。
- 修改生日时，还会检查已有账号的申请日期；不允许把生日改到申请日期之后。
- 姓名、所在地和昵称不能为空或全为空白字符。资料修改先完成全部校验，再整体替换，失败不会留下半份新资料。
- 业务拒绝使用 invalid_argument；调用方捕获并显示信息。编号耗尽使用 overflow_error，内部不一致使用 logic_error。

业务对象默认在构造时读取本机日期，测试可以显式传入固定日期。长时间运行跨日后应重建业务对象以刷新参考日期；后续可按需要改成每次读取日期。历史申请日期可通过 openService 的第 4 个参数传入，用于预置数据演示。

注册年龄按完整周年：2020-09-10 申请的账号在 2026-09-09 为 5 年，到 2026-09-10 为 6 年。2 月 29 日申请的账号，在非闰年采用 3 月 1 日计满周年的约定。

## 账号归属与后续认证约定

绑定和昵称修改都会检查账号的 personId 是否等于 actorPersonId；绑定还要求账号类型为微信和 QQ，并拒绝重复绑定、已占用绑定及跨人关联。**这是数据归属检查，不是密码认证。** 当前 main 和测试作为可信调用方传入 actorPersonId；任何人若能任意调用此层接口并伪造该参数，就不能靠它证明自己的身份。

第 5 步已采用平台人员级凭据：每个 personId 对应一份带盐密码派生结果。首次进入某项已开通服务时验证密码，后续服务由当前认证会话确认进入。菜单不得把用户输入的编号作为 actorPersonId；操作编号统一由 SessionManager 提供。

正式注册通过 AccountService::registerAccount 同时创建人员、凭据和首个服务。原 createPerson 是底层无凭据建模接口，这样创建的人员不能直接登录，也不能凭人员编号设置或接管密码。当前不支持把不同 personId 的记录合并。

## 构建与验证

```powershell
cmake --preset local-debug
cmake --build --preset local-debug
ctest --preset local-debug
.\build\debug\bin\jlu_im.exe
```

业务实现放入 jlu_core 静态库，jlu_im 演示程序和 p1_tests 测试程序链接同一份代码。后续新增业务 .cpp 请加入 CMakeLists.txt 的 add_library(jlu_core ...) 列表。普通构建会生成演示和测试程序，但只有执行 ctest 才会运行测试。

本文对应的 12 组底层场景仍保留；第 5、6 步的 15 组认证与菜单场景，以及 5 组绑定历史场景，共 32 组通过。P1 第 7 步验收已完成，详见 [验收报告](P1第7步验收报告.md)。
